AI Engineering: LLM Fundamentals

Started 5 November 2026 · In progress · Ollama, qwen3, nomic-embed-text

A large language model only guesses the next token. A loop turns those guesses into an answer, and your code does the rest: it keeps the chat history, sets the sampling options and finds related text. These notes come from phase 2 of my AI Engineering Lab.

Everything ran locally with Ollama on two PCs with no GPU (Intel i5-10210U with 31.8 GB RAM, and i5-1135G7 with 11.7 GB). The numbers are single runs unless a range is given; yours will differ.

1. The big picture

Think of IntelliJ autocomplete: you type list. and it suggests add. An LLM does the same for any text. It looks at the text so far and guesses the next piece, then runs again on the longer text:

"The cat"          → guess "sat"
"The cat sat"      → guess "on"
"The cat sat on"   → guess "the"   ... until it guesses "stop"

That loop is the whole trick. It is called autoregressive generation.

2. Tokens

The model can't read letters; it reads numbers. A tokenizer cuts text into pieces (tokens) and gives each an id, like a compiler's lexer cutting int x = 5;. The list of all pieces is the vocabulary, a Map<String, Integer>. qwen3's has 151,936 tokens.

"unbelievable"  →  ["un", "believ", "able"]  →  [403, 9182, 512]
  • Common words are one token. Rare or unknown words are split into smaller known parts.
  • For English, 1 token ≈ 4 characters ≈ ¾ of a word. Other languages and code often need more.
  • BPE builds the pieces: start with single letters, glue the pair that appears together most often (t + h → th), and repeat thousands of times. See how BPE works.
  • Price, speed and limits are all counted in tokens, like paying per MB on a cloud bill.

3. Context window and memory

Every call has a hard token limit, the context window. It must hold everything: system message + chat history + new question + the answer. Think of a max request body size on a server.

The model has no memory. Each call is a stateless REST call. A chatbot "remembers" because your code sends the whole chat again, every time:

Call 1 sends: [system, user1]
Call 2 sends: [system, user1, answer1, user2]
Call 3 sends: [system, user1, answer1, user2, answer2, user3]   ← keeps growing

Measured: asked "What is my favourite colour?" with no history, the model said "Blue.", a made-up answer, not "I don't know". With the earlier messages it said "Green.".

  • History grows every turn, and so do tokens and time.
  • When it gets too big, drop the oldest messages and keep the system one, which holds the rules. Like log rotation: old lines go, the config stays.
  • Too much data to fit at all, like 500 PDFs? Send only the useful parts. That is RAG.

4. From scores to a choice

For the next piece, the model gives a raw score to every token in the vocabulary. These scores are logits. Softmax turns them into odds that add up to 100%:

scores:   cat 2.0   mat 1.0   rat 0.5
softmax:  cat 63%   mat 23%   rat 14%

See how softmax and temperature work.

  • Always taking the top one is greedy. A weighted random pick is sampling (section 10).
  • Hallucination: the model picks what sounds right, not what is right. Like autocomplete suggesting a method that doesn't exist. Always check facts.

How a chat model is made, in three steps: pre-training on huge amounts of text to guess the next piece; instruction tuning on (question, good answer) pairs; and preference tuning, where people rank answers and the model learns which they like.

5. Running models with Ollama

Ollama downloads models and runs them on your own PC. Think of it as a local database server: it runs in the background, listens on port 11434, and your code talks to it. Models work like Docker images:

CommandDoesDocker twin
ollama pull qwen3:4bdownload a modeldocker pull
ollama listmodels on disk + sizedocker images
ollama show qwen3:4bdetails: size, context, quantizationdocker inspect
ollama run qwen3:4b "hi"load + answer one promptdocker run
ollama psmodels in RAM nowdocker ps
ollama rm qwen3:4bdelete from diskdocker rmi

qwen3:4b = family qwen3 + tag 4b, meaning 4 billion parameters (weights): numbers the model learned in training. No tag means latest. Trust ollama show, not the name: qwen3:1.7b reports 2.0B.

6. Size, RAM and speed

Quantization stores each weight in fewer bits: smaller and faster, slightly less precise. Java view: double vs float vs short vs byte. See how quantization works.

file size (GB) ≈ billions of weights × bits per weight ÷ 8
FormatBits per weightqwen3:4b sizeQuality
FP16168.0 GBoriginal
Q8_08.54.2 GBalmost the same
Q4_K_Mabout 52.5 GB (measured)small loss; Ollama's usual default

A bigger model at 4 bits usually beats a smaller one at 16. In RAM the model also needs the KV cache (memory for the text being read, which grows with the window): the 2.5 GB file used 3.2 GB in RAM, so plan with file size × 1.3.

ModelFileIn RAMLoadRead promptWrite answer
qwen3:4b2.5 GB3.2 GB9.4 s21 tokens/s7.1 tokens/s
qwen3:1.7b1.4 GB1.9 GB1.9 s63 tokens/s15.4 tokens/s
  • The writing speed is the one you feel. Half the file size gave about twice the writing speed.
  • Why so slow on a CPU? Every new token reads all the weights from RAM once. A GPU has much faster memory.
  • Ollama keeps a model in RAM for 5 minutes after a call, so the second call skips the load: 9.4 s became 0.009 s.

8. Thinking models

qwen3 writes hidden reasoning before the answer. Better on hard questions, but every thinking token costs the same time, and it counts against num_predict. Asked "What is 2+2? Answer with one number.", the answer was 4, but 99% of the tokens written were thinking.

"What is RAG?" with num_predict 60, over the API:

ModelthinkTimeResult
qwen3:1.7bnot sent12.8 s (6.3 s load)content empty: all 60 tokens were thinking
qwen3:1.7bFalse2.5 sa clean one-sentence answer
qwen3:4bnot sent19.2 s (9.2 s load)content empty
qwen3:4bFalse8.5 sthinking leaks into the answer

Hiding the thinking doesn't skip it. On the command line, --hidethinking still wrote 236 tokens to show just 4. So the chat code here uses qwen3:1.7b with "think": False.

9. Streaming

"stream": True is Ollama's default. The reply is NDJSON: one JSON object per line, each with a few characters of the answer.

{"message":{"role":"assistant","content":"R"},"done":false}
{"message":{"role":"assistant","content":"AG"},"done":false}
...
{"message":{"role":"assistant","content":""},"done":true,"done_reason":"length","eval_count":30,...}
  • The last line has done: true and the same stats as a non-streamed reply.
  • The total time is the same, but the first words came after 0.13–0.64 s instead of 2.0–3.2 s. The user reads while the model writes.
  • Read it with httpx.stream("POST", url, json=body) and iter_lines(). A plain httpx.post waits for the whole body.
  • Forget "stream": False with httpx.post and you get all the lines in one string: .json() fails with "Extra data".

See how to read a stream, with sample lines you can run.

10. Sampling

Five calls, the same prompt, "Invent an unusual name for a pet cat.":

SettingAnswers
temperature 0Zephyrclaw, Zephyrclaw, Zephyrclaw, Zephyrclaw, Zephyrclaw
temperature 0.6 (default)Squidlepus, Squidooch, Whiskerwisp, Zestraught, Zephyrclaw

The model never "chooses"; it outputs odds. Sampling then picks one, like a loot table in a game. Four settings control the pick:

logits → ÷ temperature → softmax → cut the tail (top_k, top_p) → weighted random pick (seed)

See softmax, temperature and top_p in code.

Temperature divides the scores before softmax. Same cat / mat / rat scores:

TcatmatratFeels like
0.20.990.010.00almost greedy: safe, repeats
1.00.630.230.14the model's own odds
2.00.480.290.23flatter: rare words come up often

T = 0 would divide by zero; in Ollama it acts greedy, the same answer 10 times out of 10.

JobTemperatureWhy
JSON output0one "creative" brace and parsing fails
Tool calls0the tool name must match exactly
RAG answerslowstick to the found text, don't invent
LLM as a judge0same answer, same score, every run
Chatbot small talkdefaultsome variety feels human
Names, ideas1 or moreyou want surprises
  • top_k and top_p cut the junk first. At T 1.5, one "name" came back as 'Zigguratův Nárit\n\n(Note': thousands of odd tokens each have a tiny chance, and a high T makes them bigger. top_k 2 keeps the 2 best (SQL: ORDER BY prob DESC LIMIT 2). top_p 0.8 keeps the best ones until they cover 80%: cat (0.63) + mat (0.86, stop). T 1.5 + top_p 0.1 gave Zephyrclaw five times: calm again.
  • qwen3's defaults are temperature 0.6, top_k 20, top_p 0.95. Send nothing and you get these.
  • Seed makes randomness repeatable, like new Random(42) in a JUnit test: T 1.5 + seed 42 gave "Fizzluff" five times. That is how a test with an open prompt stops being flaky.
  • The prompt sets the odds; temperature only reshapes them. Ten calls at T 1.5: "Invent a name" gave 6 different names ("Whiskers" 4 times); "Invent an unusual name" gave 9; "Name a colour" gave only Red and Blue. Answers too samey or too wild? Fix the prompt first.
  • num_predict is a hard cut, not "be short". 12 tokens gave 'Once upon a time, in a quiet village nestled between rolling'. For short answers, ask in the system prompt and keep a high limit.

11. Embeddings and search

A user types "I can't log in to my account". A note says "To reset your password, click 'Forgot password' on the login page." That is the right answer, but a keyword match (LIKE '%log in%') fails: the only shared word is "to". The fix is to find text by meaning, the core of RAG.

An embedding turns text into a list of numbers (a vector) chosen so that similar meanings get similar numbers. With nomic-embed-text it is always 768 numbers, for one word or a whole page. A chat model can't do it: qwen3:1.7b on /api/embed returned HTTP 501.

"The cat sat on the mat." → [0.05, 0.062, -0.117, -0.024, 0.052, ...]   768 numbers

Picture two numbers per text, [about animals, about money]: animal [0.9, 0.1] and kitten [0.8, 0.2] point nearly the same way; invoice [0.1, 0.9] points elsewhere. Similar meaning = arrows pointing the same way. 768 numbers is the same idea with 768 directions.

dot(a, b)    = a0*b0 + a1*b1 + ...
norm(a)      = sqrt(dot(a, a))                  # arrow length
cosine(a, b) = dot(a, b) / (norm(a) * norm(b))  # 1 same, 0 unrelated, -1 opposite

See how cosine similarity works, with a toy search in Python and numpy.

Dividing by the lengths makes a long note and a short note on the same topic score the same: dot gave 0.74 vs 7.40, cosine 1.00 for both. nomic's vectors already have length 1.0, so for them cosine = dot.

PairCosine
cat vs kitten0.84
I love this movie vs I hate this movie0.69
happy vs sad0.66
cat vs dog0.60
cat vs invoice0.40
  • Unrelated is about 0.3–0.45, not 0. Read scores as "higher than the others"; never hard-code "0.5 = match".
  • Love vs hate scores high. Embeddings measure what a text is about, not whether it is positive or true. That is why RAG still needs the LLM to read the text it found.

Search is three steps: embed every note once and keep the vectors; embed the question; score it against each note, sort best first and keep the top k.

QuestionBest noteScoreNext best
I can't log in to my accountreset password0.680.42
When do I get my bill?invoices by email0.580.44

Things that bite:

  • Use the same model for notes and question. Vectors from two models live on different maps: nonsense scores, no error.
  • Batch the call. "input" takes a list: 5 notes took 0.38–0.60 s in one call, against 1.34–1.92 s in five.
  • Different lengths are a bug. Python's zip stops at the shorter list without an error, so you get a wrong score. Make dot raise instead.
  • Prefixes. nomic's docs suggest search_query: / search_document: in front of texts. On 5 notes the result was mixed, so it needs a proper test set before deciding.

12. Check yourself

How does a chatbot remember if the model has no memory?

Your code sends the whole history again on every call. It grows each turn.

1 token is about how much English text?

About 4 characters, roughly ¾ of a word.

Logits vs softmax?

Logits are raw scores. Softmax turns them into odds that add up to 100%.

qwen3:4b at FP16 vs Q4_K_M: what size?

8.0 GB vs 2.5 GB.

Why is the second call much faster to start?

The model stays in RAM for 5 minutes: load 9.4 s became 0.009 s.

done_reason "length" means?

The answer hit num_predict and was cut off.

Why was the answer empty with num_predict 60 and no think flag?

All 60 tokens went to hidden thinking.

top_p 0.8 on cat 0.63, mat 0.23, rat 0.14 keeps what?

cat and mat: 0.63 + 0.23 = 0.86, which reaches 0.8.

Which temperature for JSON output or tool calls?

0. One "creative" token breaks parsing.

"I love this movie" vs "I hate this movie" scores 0.69. Why?

Embeddings measure what a text is about, not whether it is positive.
