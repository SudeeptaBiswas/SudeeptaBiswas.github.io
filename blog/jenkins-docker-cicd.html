CI/CD with Jenkins and Docker

10 November 2026 · Jenkins LTS, Docker Compose, Spring Boot WAR, React/Vite

One self-hosted Jenkins builds a Spring Boot backend and a React frontend into Docker images. It deploys them with Docker Compose to four environments. A new backend gets traffic only after it proves healthy, and a release moves between environments as the same image, never a rebuild.

These are my study notes from a sample pipeline I built to learn the topic, not a description of a production system. Hosts, names and repositories in it are placeholders. Sample repo: jenkins_docker_cicd (private for now).

1. The big picture

The application code lives in two separate repositories. This repository holds only the pipeline: Dockerfiles, Compose files, nginx templates, scripts, Jenkinsfiles and docs. Jenkins reads it from a bare clone that a script copies to the host over SSH, so the pipeline needs no git server.

2. Configure for separate servers

Everything runs on one host, but every part is configured as if it already had its own server. A multi-server setup runs fine on one host. A single-host setup breaks when you split it, because it leans on a shared Compose network and service names, and neither spans hosts.

  • One Compose project per part (frontend, backend, Jenkins), deployed on its own.
  • No shared Compose network. nginx finds the backend as api-server:${API_PORT}; only the address behind that name changes.
  • Every address is a variable. Moving a part to another server changes values, not design.
  • No container_name:. It is absolute and would collide between environments.

Each environment has its own ports, database schema and env files. Values are split by who reads them:

  • <env>.compose.env: tags, ports and paths for Compose. No secrets, because Compose interpolates it and mangles a $ in a password.
  • <env>.app.properties: every backend value, secrets included. Bind-mounted read-only; never in git or an image.
  • Only *.example templates are committed. The real files live on the host.

4. Blue/green backend deploy

A plain recreate of Tomcat costs about 10 to 17 seconds of errors: about 7 seconds to the first served request, plus up to 10 seconds of stop grace period. Blue/green cuts that to the second it takes to recreate nginx on the new port.

The frontend can't do the same. It owns the environment's fixed public port, so a second copy on another port is a URL nobody visits. It is replaced in place, and a failed frontend deploy stays live until someone rolls it back.

After every deploy, a Verify stage calls five paths through nginx:

PathExpectProves
/health200nginx is up
/myapp/200The app is served
/myapp/x/deep200The single-page app fallback works
/myapp/api/v1/401The proxy reached Spring Security
/nothing404404s are still 404s

5. Promotion, not rebuild

A rebuild from the same commit gives different bytes: npm ci and dnf install pull whatever is current. So the image that passed test is the one that goes to uat. The deploy job has three actions:

  • BUILD_AND_DEPLOY: check out both repositories at the same ref, build, deploy.
  • DEPLOY_EXISTING: deploy an image that already exists. This is how you promote.
  • ROLLBACK: undo the last deploy.

Each image is tagged with the build number, a UTC timestamp and both commits. To prove a promotion happened, compare image IDs:

docker inspect --format '{{.Image}}' myapp-dev1-backend-blue-api-1
docker inspect --format '{{.Image}}' myapp-test-backend-green-api-1
# identical IDs = the same binary

6. Rollback and the configuration trap

PartHow it rolls backTime
BackendRestarts the stopped container the last deploy replaced. One step back onlyAbout 8 s
FrontendRedeploys the previous image tag, recorded in the env fileAbout 1 s

The trap: a container's image, environment and ports are frozen when it is created. docker start re-reads nothing. So after you rotate a database password, a backend rollback brings back the old password. The pipeline checks for this first: a compare script exits 0 when the settings match, 3 on drift and 1 on error, and the rollback refuses on drift unless forced.

To go back more than one step, deploy an older tag with DEPLOY_EXISTING.

7. Backups and host safety

Jenkins home (jobs, build history, credentials, plugins) is the only thing not rebuilt from git. A script stops Jenkins for about 9 seconds, tars the named volume with a short-lived helper container, and starts Jenkins again. Releases deployed to test and uat are also saved with docker save, so the approved binary survives the loss of the image store.

Never run on the hostBecause
docker compose down -vDeletes volumes: maybe a database or Jenkins home
docker volume pruneTakes Jenkins home with it
docker image pruneDeletes the frontend's rollback image, which no container holds

Jenkins holds the Docker socket, which is root on the host. So it stays on the LAN, takes no webhooks, and gets as few plugins as possible.

8. What a review found

A code review of the sample found 10 bugs, most of them in rollback. Three lessons:

  • Test every path a parameter can take. The job's FORCE option was never passed to the frontend rollback script, so it did nothing there, and the job still reported success.
  • Snapshot what is running, not what is on disk. Settings copied from the env file at deploy time may already be edited. docker inspect on the running container is the true record.
  • "The check failed" is not "the check passed". Handle every exit code a guard can return, not just the one you expect.

9. Check yourself

Why promote an image instead of rebuilding it?

A rebuild gives different bytes, so the sign-off would cover a binary nobody tested.

How does blue/green avoid downtime on the backend?

The new colour starts on a spare port. nginx is pointed at it only after its health check passes.

Why doesn't the frontend use blue/green too?

It owns the fixed public port. A second copy on another port would be a URL nobody visits.

A backend rollback brings back an old password. Why?

Container settings are frozen when it is created, and docker start re-reads nothing.

Why keep secrets out of the Compose env file?

Compose interpolates it, so a $ in a password is silently mangled.

Why is docker image prune dangerous here?

The frontend's rollback image is named only in an env file, not held by a container, so prune deletes it.
