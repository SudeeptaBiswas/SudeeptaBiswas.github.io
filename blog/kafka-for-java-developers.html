Apache Kafka for Java Developers

1 November 2026 · Kafka 3.x/4.x, Spring Boot 3, spring-kafka

Kafka is a distributed event log. Services write events to it, and other services read them in order, at their own pace. This post covers the parts you need before writing your first Spring Boot producer and consumer.

These are my study notes, not production experience. I wrote them to learn the topic properly. Please check the official docs (links at the end) before using them in a real system.

1. When to use Kafka

Use Kafka when many systems need the same stream of events, and when you may need to replay past events. Kafka does not delete an event when someone reads it. It keeps events for a set time, for example 7 days.

  • Good fit: order events read by billing, analytics and audit; activity logs; data pipelines.
  • Weaker fit: a simple job queue where one worker takes each task and then it is gone. A broker like RabbitMQ is often simpler there. See my RabbitMQ notes.

2. The big picture

3. Core components

ComponentWhat it is
RecordOne event: key, value, headers, timestamp.
TopicA named stream of records, e.g. orders. Append-only.
PartitionAn ordered log. A topic is split into partitions so it can scale. Order is kept only inside one partition.
OffsetThe position of a record in a partition. A consumer saves its offset to know where it stopped.
ProducerWrites records. Records with the same key go to the same partition, so their order is kept.
Consumer groupConsumers with the same group id share the partitions. Different groups each get all the data.
Broker / clusterA broker is one Kafka server. A cluster is several brokers working together.
Replica, leader, followerEach partition is copied to other brokers. The leader handles reads and writes; followers copy it and take over if it fails.
ISRIn-sync replicas: followers that are fully caught up. Only they can become leader.
KRaft controllerManages cluster metadata and leader election. Built into Kafka 3.x. It replaced ZooKeeper, which Kafka 4.0 removed.

4. Data rules: retention, acks, delivery

  • Retention: records stay for a set time or size. Reading does not delete them.
  • Log compaction: keeps only the latest record per key. Useful for "current state" topics.
  • acks (producer safety): 0 = don't wait, 1 = leader wrote it, all = all in-sync replicas wrote it (safest).
  • Rebalance: partitions are re-assigned when a consumer joins or leaves a group.
  • Delivery: at-most-once, at-least-once (the usual default), or exactly-once (idempotent producer + transactions).

A safe default for important data: replication factor 3, acks=all, min.insync.replicas=2, idempotent producer, and commit offsets after processing.

5. How a write and a read work

  1. The producer sends (key, value) with acks=all to the partition leader.
  2. The leader appends the record to its log.
  3. Followers fetch the new record. When all in-sync replicas have it, the leader acks the producer.
  4. A consumer polls from its last offset, e.g. 42, and gets records 42 to 50.
  5. After processing them, the consumer commits offset 51.

6. Spring Boot example

Add spring-kafka. Use KafkaTemplate to send and @KafkaListener to consume.

# application.yml
spring:
  kafka:
    bootstrap-servers: localhost:9092
    producer:
      acks: all                       # wait for all in-sync replicas
      key-serializer: org.apache.kafka.common.serialization.StringSerializer
      value-serializer: org.springframework.kafka.support.serializer.JsonSerializer
      properties:
        enable.idempotence: true      # no duplicates when the producer retries
    consumer:
      group-id: billing
      auto-offset-reset: earliest     # a new group starts from the beginning
      enable-auto-commit: false       # commit only after processing
      key-deserializer: org.apache.kafka.common.serialization.StringDeserializer
      value-deserializer: org.springframework.kafka.support.serializer.JsonDeserializer
      properties:
        spring.json.trusted.packages: "com.example.order"
    listener:
      ack-mode: record                # commit after each record succeeds
@Configuration
class KafkaTopics {
    @Bean NewTopic orders() {                        // created at startup if missing
        return TopicBuilder.name("orders").partitions(3).replicas(3).build();
    }
}

@Service
class OrderProducer {
    private final KafkaTemplate<String, OrderEvent> kafka;
    OrderProducer(KafkaTemplate<String, OrderEvent> kafka) { this.kafka = kafka; }

    void publish(OrderEvent e) {
        // key = customerId: same partition, so order is kept per customer
        kafka.send("orders", e.customerId(), e)
             .whenComplete((res, ex) -> {
                 if (ex != null) log.error("send failed", ex);
                 else log.info("partition {} offset {}",
                         res.getRecordMetadata().partition(),
                         res.getRecordMetadata().offset());
             });
    }
}

@Component
class BillingConsumer {
    @KafkaListener(topics = "orders", groupId = "billing", concurrency = "3") // 3 threads, 3 partitions
    void onOrder(OrderEvent e) {
        billingService.charge(e);   // must be idempotent: the same record can arrive twice
    }
}

record OrderEvent(String orderId, String customerId, BigDecimal amount) {}

Note: replicas(3) needs at least 3 brokers. With the one-broker Docker setup in section 8, use replicas(1).

For retries, add @RetryableTopic(attempts = "3") to the listener. Records that still fail go to a dead-letter topic, orders-dlt.

7. Plain Java client

Without Spring, so you can see the basics:

Properties p = new Properties();
p.put("bootstrap.servers", "localhost:9092");
p.put("key.serializer", StringSerializer.class.getName());
p.put("value.serializer", StringSerializer.class.getName());
p.put("acks", "all");
try (var producer = new KafkaProducer<String, String>(p)) {
    producer.send(new ProducerRecord<>("orders", "cust-42", "{\"orderId\":\"o1\"}"));
}

Properties c = new Properties();
c.put("bootstrap.servers", "localhost:9092");
c.put("group.id", "billing");
c.put("enable.auto.commit", "false");
c.put("key.deserializer", StringDeserializer.class.getName());
c.put("value.deserializer", StringDeserializer.class.getName());
try (var consumer = new KafkaConsumer<String, String>(c)) {
    consumer.subscribe(List.of("orders"));
    while (true) {
        for (var r : consumer.poll(Duration.ofMillis(500))) {
            System.out.printf("p%d off%d %s=%s%n", r.partition(), r.offset(), r.key(), r.value());
        }
        consumer.commitSync();      // after processing: at-least-once
    }
}

8. Try it locally with Docker

One broker in KRaft mode, no ZooKeeper:

docker run -d --name kafka -p 9092:9092 apache/kafka:3.9.0

# create a topic with 3 partitions
docker exec -it kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --create --topic orders --partitions 3

# type key:value lines to send
docker exec -it kafka /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic orders \
  --property parse.key=true --property key.separator=:

# read them as group "billing"
docker exec -it kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic orders --group billing \
  --from-beginning --property print.key=true

# see consumer lag
docker exec -it kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group billing

9. Common pitfalls

  • No key: records spread across partitions, so there is no order per customer.
  • Auto-commit before processing: if the app crashes, the record is lost. Commit after processing and make the consumer idempotent.
  • More consumers than partitions: the extra consumers sit idle.
  • Slow processing: longer than max.poll.interval.ms and the consumer is removed from the group, which causes repeated rebalances.
  • Adding partitions later: changes which partition a key goes to, so order breaks for existing keys.

10. Check yourself

How does Kafka keep order?

Only inside one partition. Use the same key for related events so they land in the same partition.

How do you scale consumers?

Add partitions and consumers in one group. The maximum useful consumers per group equals the number of partitions.

How do you avoid data loss?

Replication factor 3, acks=all, min.insync.replicas=2, idempotent producer, commit after processing.

How do you get exactly-once?

Inside Kafka: idempotent producer plus transactions. When writing outside Kafka, e.g. to a database: at-least-once plus an idempotent consumer.

What is consumer lag?

Latest offset minus committed offset. If it keeps growing, consumers are too slow.

Kafka or RabbitMQ?

Kafka keeps a stream that many systems read and replay. RabbitMQ delivers each job to one worker reliably. See the comparison table.
