Messaging

RabbitMQ for Java Developers

5 October 2026 · RabbitMQ 4.x, AMQP 0-9-1, Spring AMQP

RabbitMQ is a message broker. Producers send messages to an exchange. The exchange routes them to queues. Consumers take messages from a queue and confirm them. Once confirmed, a message is gone. This is the main difference from Kafka.

1. The big picture

The labels on the arrows are binding keys. * matches one word and # matches zero or more words. A message the alerts consumer rejects can go to a dead-letter exchange and wait in a separate queue for someone to look at it.

2. Core components

ComponentWhat it is
MessageBody (bytes) plus properties: headers, routing key, delivery mode, TTL, correlation id.
ProducerPublishes messages to an exchange, never directly to a queue.
ExchangeThe router. Sends copies to bound queues based on its type and the routing key.
QueueStores messages until a consumer confirms them. First in, first out.
BindingA rule that links an exchange to a queue, with a key or pattern.
Routing keyA label on the message, e.g. order.created, matched against bindings.
Ack / nackAck: the consumer is done, so the message is deleted. Nack or reject: requeue it or dead-letter it.
Prefetch (QoS)The most unconfirmed messages one consumer can hold. Keeps the load fair.
Connection / channelOne TCP connection carries many light channels, usually one per thread.
Virtual hostA separate space with its own exchanges, queues, users and permissions.
Dead-letter exchangeWhere rejected, expired or overflowing messages go.

3. Exchange types

TypeHow it routesUse for
DirectRouting key must equal the binding keyA task for one kind of worker, e.g. pdf.generate
TopicPattern match with * and #Events by category: order.*, *.failed
FanoutIgnores the key; copies to every bound queueBroadcast: cache refresh, notifications
HeadersMatches message headers instead of the keyRare; routing on several attributes
DefaultRouting key = queue nameSimple "send to queue X"

4. Reliability: not losing messages

  • Durable queue + persistent message (delivery mode 2): survives a broker restart.
  • Publisher confirms: the broker tells the producer when the message is safely stored.
  • Manual ack after the work is done, not auto-ack. If the consumer crashes, the message is delivered again.
  • Delivered again means at-least-once, so consumers must be idempotent, e.g. skip a message id they have already seen.
  • Quorum queues are copied to 3 or more nodes using Raft. They are the default choice for high availability. RabbitMQ 4.0 removed the old classic mirrored queues.
  • Dead-letter exchange + TTL: retry after a delay, and park "poison" messages in a dead-letter queue.
  • Ordering is kept per queue with one consumer. It is lost with many competing consumers or requeues.

5. Spring Boot example

Add spring-boot-starter-amqp. Use Jackson2JsonMessageConverter for JSON.

@Configuration
class RabbitConfig {
    @Bean TopicExchange events() { return new TopicExchange("events"); }

    @Bean Queue billing() {
        return QueueBuilder.durable("billing").deadLetterExchange("dlx").build();
    }

    @Bean Binding billingBinding(Queue billing, TopicExchange events) {
        return BindingBuilder.bind(billing).to(events).with("order.*");
    }
}

// producer
rabbitTemplate.convertAndSend("events", "order.created", orderDto);

// consumer: acked when the method returns without an exception
@RabbitListener(queues = "billing")
void onOrder(OrderDto o) { billingService.charge(o); }

Tune spring.rabbitmq.listener.simple.prefetch and the retry settings in application.yml.

6. RabbitMQ vs Kafka

RabbitMQKafka
ModelSmart broker: routes, deletes after ackSimple broker: append-only log; consumers track their offset
RoutingRich: exchanges, patterns, headersTopic + partition key only
ReplayNo, once acked it's gone (the Streams feature adds a log)Yes, re-read any offset within retention
OrderingPer queue, with one consumerPer partition
ThroughputHighVery high, built for large streams
Scale consumersAdd consumers to a queueAdd partitions (max consumers per group = partitions)
Best forTask queues, request/reply, complex routingEvent streams, logs, analytics, many readers

In one line: RabbitMQ delivers each job to a worker reliably. Kafka keeps a stream of events that many systems read and replay.

7. Where it fits in a business app

Take an imaginary online shop built with Spring Boot:

  • Invoices: the PDF invoice job goes to an invoice.generate queue and a worker builds it. The API thread stays free, and the UI polls for status.
  • Emails: order confirmations go on a queue. If sending fails, retry through a dead-letter exchange instead of failing the customer's request.
  • Order events: publish to a topic exchange with order.* keys, so billing, shipping and audit can each bind their own queue.

8. Check yourself

Exchange vs queue?

The exchange routes. The queue stores.

Direct, topic, fanout: give an example of each.

See section 3.

How do you avoid losing messages?

Durable queue, persistent message, publisher confirms, manual ack, quorum queue.

A consumer crashes mid-work. What happens?

No ack, so the message is delivered again. That's why the consumer must be idempotent.

A poison message keeps failing. What do you do?

Limit retries, then send it to a dead-letter queue and alert someone.

At-most, at-least, exactly-once?

Auto-ack gives at-most-once. Manual ack gives at-least-once. "Exactly-once" in practice = at-least-once + an idempotent consumer.
